# EasyGo — Real GPS Tracker Device Setup & Integration Specification

This document defines the vendor-neutral technical specification for connecting physical GPS tracking devices (installed inside transit buses) to the EasyGo Real-Time Transit Platform.

> **Hardware Independence Notice**: EasyGo uses a decoupled GPS Adapter ingestion architecture. The platform does not depend on any single tracker manufacturer or proprietary vendor cloud. Any commercial or industrial 4G/LTE GPS tracker capable of making HTTP/HTTPS POST requests or configurable with an HTTP gateway can connect directly to EasyGo.

---

## 1. Server URL & Public Addressing
For field operation, the EasyGo backend must be reachable via a public Fully Qualified Domain Name (FQDN) secured with a valid TLS certificate:

- **Production URL**: `https://api.easygo.yourdomain.com`
- **Staging / Testing URL**: `https://staging-api.easygo.yourdomain.com`
- **Local Dev / Bench Test URL**: `http://<LAN_IP_OR_HOST>:3000`

---

## 2. GPS Endpoints
EasyGo exposes two dedicated endpoints for GPS hardware telemetry:

| Endpoint | HTTP Method | Purpose |
| :--- | :--- | :--- |
| `/gps/location` | `POST` | Ingests real-time coordinate telemetry (lat, lng, speed, heading, accuracy, timestamp). |
| `/gps/heartbeat` | `POST` | Liveness ping when the vehicle is stationary / parked (battery, GSM signal, firmware). |

---

## 3. Port & Networking
- **HTTPS Port**: `443` (Standard HTTPS)
- **HTTP (Dev/Testing only)**: `80` or `3000`
- **Firewall Rule**: Allow inbound TCP traffic on port `443` from the cellular network carrier APN / cellular IP range.

---

## 4. HTTPS Requirement
- **Production Requirement**: **MANDATORY HTTPS (TLS 1.2 or TLS 1.3)**.
- Plain HTTP is strictly forbidden in production to protect against man-in-the-middle attacks, credential snooping, and telemetry tampering.
- The physical GPS device modem must support TLS 1.2+ and have public root Certificate Authority (CA) certificates installed (or be configured with an intermediate hardware IoT forwarder proxy).

---

## 5. Authentication Model
EasyGo implements dual-layer hardware authentication:

1. **Tracker Identification**: Each physical hardware unit must identify itself using its assigned `trackerId` (e.g., `TRK001`) or hardware `deviceId` (e.g., IMEI).
2. **Device Secret / API Key**: Each tracker is provisioned with a secure secret key generated by the EasyGo Admin API upon onboarding.

### Authentication Credentials Transmission:
The device must transmit its secret key via HTTP headers or Authorization header:

- **Primary Header**: `x-tracker-key: <DEVICE_SECRET>`
- **Identification Header**: `x-tracker-id: <TRACKER_ID>`
- **Standard Authorization Fallback**: `Authorization: Bearer <DEVICE_SECRET>` or `Authorization: ApiKey <DEVICE_SECRET>`

*Never send device secret keys over unencrypted HTTP.*

---

## 6. Tracker ID Format
- **Format**: Alphanumeric string with optional underscores or dashes: `^[A-Za-z0-9_-]{3,32}$`.
- **Examples**:
  - `TRK001`, `TRK002`, `TRK_12A_01`
  - IMEI: `864209041234567`
- Recommended naming convention for fleets: `TRK` prefix followed by 3-digit zero-padded number (e.g., `TRK001`, `TRK002`).

---

## 7. Request Headers
Every HTTP POST request sent by the tracker must include:

```http
POST /gps/location HTTP/1.1
Host: api.easygo.yourdomain.com
Content-Type: application/json
x-tracker-key: trk001-secret-key
x-tracker-id: TRK001
Connection: keep-alive
User-Agent: EasyGo-GpsClient/1.0
```

---

## 8. JSON Payload Specification

### `POST /gps/location` Payload Schema:
```json
{
  "trackerId": "TRK001",
  "latitude": 10.960145,
  "longitude": 76.950232,
  "speed": 34.2,
  "heading": 142.5,
  "accuracy": 4.2,
  "timestamp": "2026-09-30T10:15:30.000Z",
  "batteryLevel": 98,
  "gsmSignal": 28,
  "satellites": 11,
  "ignition": true
}
```

### Field Definitions:
| Field | Type | Required | Range / Format | Description |
| :--- | :--- | :--- | :--- | :--- |
| `trackerId` | String | Conditional | `TRK001` | Logical tracker ID (required if not passed in header). |
| `latitude` | Float | **Yes** | `-90.0` to `+90.0` | WGS84 decimal latitude. |
| `longitude` | Float | **Yes** | `-180.0` to `+180.0` | WGS84 decimal longitude. |
| `speed` | Float | Optional | `>= 0` (km/h) | Ground speed in kilometers per hour. Default: `0`. |
| `heading` | Float | Optional | `0.0` to `360.0` | Compass heading / bearing in degrees. Default: `0`. |
| `accuracy` | Float | Optional | `>= 0` (meters) | Estimated horizontal accuracy in meters (HDOP). |
| `timestamp` | String | **Yes** | ISO 8601 UTC | Example: `2026-09-30T10:15:30.000Z`. |
| `batteryLevel`| Number | Optional | `0` to `100` | Device backup battery percentage. |
| `gsmSignal` | Number | Optional | `0` to `31` or CSQ | Cellular signal strength indicator. |
| `satellites` | Number | Optional | `0` to `32` | Number of GPS satellites locked in fix. |

---

## 9. Latitude & Longitude Format
- Coordinates must strictly be **WGS84 decimal degrees** (standard GPS coordinate system used by Google Maps).
- Precision: 5 to 6 decimal places (~1 meter resolution).
  - Example: `10.960145` (Lat), `76.950232` (Lng).
- *Do NOT send NMEA degrees-minutes format (`1057.6087N`) directly without decimal conversion.*

---

## 10. Timestamp Format
- Standard: **ISO 8601 UTC string** (`YYYY-MM-DDTHH:mm:ss.sssZ`).
- Example: `2026-09-30T10:15:30.000Z`.
- Device clocks must synchronize via GPS satellite time or NTP (Network Time Protocol).
- Rejection policy:
  - Timestamps > 5 minutes in the future are rejected (`400 Bad Request`).
  - Timestamps > 24 hours in the past are rejected (`400 Bad Request`).

---

## 11. Recommended Location Update Interval
Configure the GPS device update rate depending on vehicle movement status:

| Vehicle State | Detection Criteria | Recommended Interval |
| :--- | :--- | :--- |
| **Moving on Route** | Speed > 5 km/h or Ignition ON | **Every 3 to 5 seconds** |
| **Stopped at Bus Stop / Traffic** | Speed < 5 km/h for > 15s | **Every 10 to 15 seconds** |
| **Parked / Depot (Ignition OFF)** | Ignition OFF > 5 min | **Heartbeat every 60 to 120 seconds** |

*A 3 to 5-second interval provides smooth live bus marker movement on Flutter Google Maps while optimizing cellular data usage.*

---

## 12. Heartbeat Interval
When the vehicle is idle or parked:
- Endpoint: `POST /gps/heartbeat`
- Frequency: **Every 60 seconds** (configurable up to 300s).
- Keeps the server-side device status marked as `ONLINE` without generating unnecessary database route location rows.

---

## 13. Retry Rules & Exponential Backoff
When the GPS device fails to reach the backend (e.g., cellular dead-zone or tunnel):
1. **Never Crash the Device Loop**: Failures must be caught and logged locally.
2. **Local FIFO Queue**: Store unsent location points in internal flash/RAM buffer (FIFO queue).
3. **Retry Strategy**:
   - Initial retry after 2 seconds.
   - Increment backoff: 2s → 4s → 8s → 16s (cap at 30 seconds).
4. **Queue Flushing**: Once cellular connection is restored, transmit buffered packets in chronological order.

---

## 14. Offline Behavior & Packet Ordering
EasyGo enforces strict packet protection:
- **Out-of-Order Rejection**: If Packet B has a timestamp older than Packet A, Packet B will be recorded for historical analytics but will **NOT** overwrite the real-time live map location or reverse route progression.
- **Duplicate Suppression**: If identical coordinates with the same timestamp are retried, EasyGo safely acknowledges without duplicating database records or jumping the live map.

## 17. Error Codes

| HTTP Status | Error Code | Root Cause & Resolution |
| :--- | :--- | :--- |
| `400 Bad Request` | `Invalid coordinates` | Latitude not in [-90, 90] or Longitude not in [-180, 180]. Check device format. |
| `400 Bad Request` | `Invalid timestamp` | Timestamp not valid ISO 8601, > 5m in future, or > 24h old. Synchronize device clock. |
| `401 Unauthorized` | `Invalid tracker API key` | `x-tracker-key` is missing or does not match the device secret configured on the server. |
| `403 Forbidden` | `Tracker device is inactive` | The tracker has been deactivated by an admin. Check tracker status via Admin API. |
| `403 Forbidden` | `Tracker is not assigned` | The tracker is registered but not linked to a bus. Assign tracker using Admin API. |
| `429 Too Many Requests` | `Rate limit exceeded` | Tracker sending too frequently (> 20 req/sec). Adjust device interval to 3-5 seconds. |
| `500 Internal Error` | `Internal Server Error` | Database/Redis temporary issue. Device should retry after backoff. |

## 18. How to Assign Tracker to a Bus

Once the physical hardware is installed on a bus:

### Step 1: Onboard Tracker in EasyGo
Make an Admin API call:
```bash
POST /admin/trackers
Headers:
  x-admin-key: <ADMIN_SECRET_KEY>
  Content-Type: application/json
Body:
{
  "trackerId": "TRK001",
  "deviceName": "Bus 12A Physical Tracker",
  "busId": "BUS_12A"
}
```
*The response returns the generated `deviceSecret`. Configure this secret in the physical tracker's configuration portal.*

### Step 2: Reassigning or Replacing a Tracker
If a physical unit fails and is replaced:
```bash
POST /admin/trackers/TRK002/assign
Headers:
  x-admin-key: <ADMIN_SECRET_KEY>
  Content-Type: application/json
Body:
{
  "busId": "BUS_12A"
}
```
*EasyGo automatically unassigns the old `TRK001`. The old tracker immediately loses permission to update Bus 12A.*
